# Quality Engine и устойчивый Auto

## Цель

Стандартный sing-box `urltest` выбирает узел по последнему измерению и `tolerance`. Этого достаточно для базового Auto, но недостаточно для мобильной сети: один случайный скачок задержки может менять эффективный outbound, а повторные ошибки не создают управляемого периода восстановления.

Ninety добавляет отдельный platform-neutral policy layer `:core:quality`. libbox по-прежнему выполняет URLTest и предоставляет задержки; Quality Engine только хранит историю, оценивает здоровье нод и решает, стоит ли менять закреплённую рекомендацию.

## Поток данных

```text
libbox urltest group
        ↓
ClashMonitor: tag -> node id
        ↓
QualityEngine.observe(batch)
        ↓
history + ratings + stable recommendation
        ↓
DataStore quality_json
        ↓
ConfigBuilder: Auto -> recommended concrete node
        ↓
serialized VpnService reload when recommendation changed
```

Пользовательский выбор в `Store` остаётся `Auto`. Конкретная нода используется только при построении runtime-конфига. Поэтому ручной выбор ноды никогда не перезаписывается движком.

## Валидность измерений

Успешная задержка находится в диапазоне `1..64999` мс.

Следующие значения считаются ошибкой:

- отсутствующий delay;
- `0`;
- отрицательное значение;
- `>= 65000`.

Каждый завершённый batch добавляет ровно один sample на кандидата. История ограничена последними 12 samples на ноду.

## Health score

Для доступной ноды вычисляются:

- median latency;
- p90 latency;
- jitter как `p90 - median`;
- success rate по ограниченной истории;
- число последовательных ошибок;
- cooldown state.

Базовая оценка равна 100 и уменьшается штрафами:

```text
latency penalty = min(60, median / 25)
jitter penalty  = min(20, jitter / 40)
failure penalty = min(35, (100 - successRate) * 35 / 100)
score           = clamp(100 - penalties, 1..100)
```

Нода получает score `0`, если:

- нет ни одного успешного sample;
- последний успешный sample старше 30 минут;
- действует cooldown.

При одинаковой оценке используются median latency и затем стабильный node id. Поэтому одинаковый вход всегда даёт одинаковый результат.

## Hysteresis и переключение

Первый валидный batch не вызывает немедленный переход на самый низкий ping. Текущий effective node группы libbox становится incumbent. Это исключает скачок сразу после запуска.

Challenger заменяет доступный incumbent только когда одновременно выполнены условия:

1. у challenger не менее двух успешных samples;
2. прошло минимальное время удержания incumbent — по умолчанию 90 секунд;
3. score challenger выше score incumbent минимум на 8 пунктов.

Если incumbent недоступен или попал в cooldown, движок может выбрать лучший доступный узел немедленно.

## Ошибки и cooldown

По умолчанию cooldown начинается после двух последовательных ошибок.

Первый cooldown равен 60 секундам. Каждая следующая непрерывная ошибка удваивает длительность до установленного максимума:

```text
60s -> 120s -> 240s -> ...
```

Успешный sample сбрасывает consecutive failures и cooldown для ноды.

## Persisted state

История хранится отдельно от пользовательских VPN options:

- DataStore key: `quality_json`;
- SharedPreferences key с тем же именем используется как rollback copy;
- формат версионирован;
- максимум 64 профиля;
- максимум 512 нод на профиль;
- максимум 12 samples на ноду.

История разделена по profile id. При удалении профиля или обновлении подписки записи отсутствующих нод удаляются. Room schema не меняется.

Persisted recommendation применяется только если её свежий rating остаётся доступным. После 30 минут без успешного измерения старт использует обычный raw `urltest` до нового batch, а не слепо доверяет старой ноде.

## Runtime guarantees

- ручной выбор ноды никогда не заменяется Quality Engine;
- при выключенном Quality Engine используется обычный `ProxySelection.Auto`;
- reload запрашивается только при реальном изменении рекомендации;
- между автоматическими reload действует дополнительный защитный интервал 5 секунд;
- start/reload/stop продолжают проходить через generation-safe FIFO runtime;
- устаревшая рекомендация не становится selector default;
- raw ping остаётся видимым отдельно от исторического Q-score.

## UI

Экран Ноды показывает:

- последний raw ping;
- `Q0..Q100` — историческую оценку;
- success rate;
- jitter;
- выделение рекомендованной ноды;
- `QUALITY` и `Стабильно → ...` в карточке Auto после появления свежей рекомендации.

До первой свежей рекомендации карточка Auto остаётся в режиме `URLTEST`.

## Автоматические тесты

`:core:quality:test` проверяет:

- привязку первого решения к текущей effective node;
- запрет раннего switch;
- switch только после dwell, достаточной истории и margin;
- немедленную замену недоступного incumbent;
- экспоненциальный cooldown;
- сброс failures после успеха;
- ограничение истории;
- детерминированный tie-break.

Data tests дополнительно подтверждают, что `qualityJson` не теряется при нормализации storage snapshot.

## Обязательная проверка на реальном устройстве

Перед ready-for-review выполнить:

1. Подключить профиль минимум с тремя рабочими нодами и выбрать Auto.
2. Убедиться, что первый batch закрепляет текущую effective node, а не вызывает несколько последовательных reload.
3. Запустить несколько ручных тестов при близких ping и проверить отсутствие флаппинга.
4. Создать явно более быстрый challenger и проверить switch только после двух samples и dwell.
5. Сделать incumbent недоступным и проверить переход после порога ошибок.
6. Проверить рост cooldown при продолжающихся ошибках.
7. Вернуть ноду в сеть и проверить сброс failures после успешного sample.
8. Перезапустить приложение раньше 30 минут и проверить восстановление свежей истории.
9. Проверить, что устаревшая история старше 30 минут не закрепляет ноду до свежего URLTest.
10. Выбрать ноду вручную и убедиться, что Quality Engine её не меняет.
11. Переключить профиль и проверить независимость recommendation/history.
12. Обновить подписку с удалёнными нодами и проверить pruning.
13. Проверить Wi-Fi → mobile → Wi-Fi, sleep/wake и потерю сети.
14. Проверить start/stop/reload/revoke при активном Auto.
15. Проверить Compact/Medium/Expanded экран Ноды и длинные имена нод.

До прохождения этой матрицы PR остаётся draft.
